# 人工审校反馈回流

仅在分析审校表、计算改动率或根据反馈更新 Skill/Profile 时使用。

## 先确定比较对象

- 读取实际列值、表头和 Note 引文，确认 MT、LQE 建议、老师终稿分别是哪一列。
- 自由 Note 中的“LQE”“原译”等称呼只能作为线索；引文或问题描述必须与对应列内容对齐。
- 分开统计字面改动、格式改动和有问题证据支持的改动。不得把 `Final != LQE` 直接称为 LQE 错误率。
- 空白 Note 固定表示 `unknown`，不能解释为接受、无问题或反对。

## 互斥分类

每条反馈只选一个主类，并保留次要标签：

| 主类 | 含义 | 可否直接回流 |
|---|---|---|
| `objective_error` | 可由源文、目标语语法或已确认事实证明的错误 | 可进入通用机制或项目规则 |
| `project_style` | 已确认且可重复执行的项目语体、称谓、时代或格式规范 | 仅进入对应 Profile，必须带作用域 |
| `editorial_preference` | 多种成立表达中的个人润色选择 | 不得硬化；最多作为非运行时参考 |
| `source_context` | 源文疑误、缺上下文或依赖客户选择 | 保持待确认，不自动学习 |
| `reviewer_regression` | 审校终稿新引入语义、语法或格式问题 | 作为负例，不得作为 preferred target |
| `no_change` | 规范化后没有实质改动 | 不计入实际修改 |

## 回流边界

- 通用、确定且跨项目成立的形式约束进入 Skill，例如空白、成对标点和可证明的助词形态。
- 人物语体、旁白体、称谓、时代词和场景物件进入项目 Profile，不得写死在通用 Skill。
- Profile 规则必须保存 `authority`、`provenance`、明确 `scope`，并使用 `confirmed` 状态；未知受话人、关系阶段或场景不得补猜。
- 新规则与现有规则冲突时先显式替换、降级或限定作用域；不得让两个相反的 confirmed 规则同时生效。
- 整句终稿不是绝对真值。回流前重新核对参与者、动作、否定、数量、时态、强度、确定度、视角、物件类型和话语功能。
- 风格改写只能修改实现风格所需的跨度；不得顺便改变上述语义锚点。

## 验证口径

- 客观错误率与项目风格不符合率分别报告，个人偏好和审校回归单列。
- 规则提炼集不能兼作效果证明；用未参与规则编写的场景或后续批次做留出验证。
- 未运行回归时必须明确写“仅完成实现与静态/定向验证”，不得据此声称质量率已经下降。
