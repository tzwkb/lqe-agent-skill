# LQE 上下文管线开发文档

版本：Context Architecture v2
日期：2026-08-15
基线 commit：`336b9c0f6821ee7edd532eeec7f20309c37b6f6a`
验证结果：clean commit `336b9c0`；internal devkit 的 unittest 729/729、原生回归 160/160、六个 base/off 与六个 shadow profile smoke 全部通过，coverage 全部 `unmapped=0`。Enforce 只对五个存在非空 context 的 profile 验证；Ananta 不运行 enforce。

## 1. 文档范围

本文说明 LQE Context v2 的已实现通用架构、数据合同、运行顺序、失败边界和扩展方法。它面向开发、运维和 profile 维护者，不包含项目私有资料、人工终稿或任何可反推客户内容的样例。

### 1.1 目标

- 保真读取业务 key、文本类型、说话人、受话人、场景和其他已声明字段。
- 将风格、实体、关系、审核案例、情境规则与术语拆成可追溯的类型化资产。
- 为每个 checker 交付同一事实源派生的模块投影，并记录它实际使用的证据。
- 让建议生成器使用 checker 已选证据的严格并集，不重新选取有利上下文。
- 将建议译文拆成 source-first 生成、确定性校验、独立 verifier 和 final 发布四个责任边界。
- 任何输入、规则、证据、保护状态或运行版本变化后，拒绝复用过期 artifact。

### 1.2 非目标

- 不从台词或目标语表面形式猜测客户未提供的人物、关系或场景事实。
- 不让每个 worker 各自解析原始 XLSX、DOCX 或其他客户资料。
- 不把一条人工反馈自动提升为全项目规则。
- 不把建议译文自动写入 corrected 文件或应用到原译。
- 不以第二次完整 LQE 代替候选验收；verifier 只验证已有候选。
- 不在核心 Python 中写入项目名、人物名、剧情枚举或某目标语硬编码规则。

## 2. 总体架构

```text
原始项目资料
  → profile ingest / source manifest / coverage
  → canonical typed assets
  → asset snapshot + capability resolution

待审文件
  → format adapter + input guard
  → normalized segments + provenance
  → project canonical override
  → verified job sidecar
  → language/context rules
  → segment revision + module equivalence keys
  → split generation
  → module context bundles + worker manifests
  → checker packets + selected evidence index
  → bound module publications
  → verified errors + score
  → source-first suggestion candidates
  → independent verifier
  → report-only final suggestions
  → report v6 / corrected export
```

管线分为六层：

| 层 | 职责 | 主要产物 |
|---|---|---|
| 声明层 | 项目身份、资产、能力、模块视图 | normalized profile、asset snapshot、capability resolution |
| 输入层 | 格式解析、列绑定、稳定身份、来源证明 | state、source manifest、input guard |
| 上下文层 | 资产筛选、逐句投影、规则解析、邻句边界 | context bundle、resolved constraints |
| 审校层 | 模块分工、证据绑定、worker 身份与全 ID 覆盖 | review packet、evidence index、module receipt |
| 建议层 | 源文语义重建、候选路由、独立验收、final 发布 | generation/candidate/review/final artifacts |
| 交付层 | 计分、报告、导出、隐藏审计合同 | errors contract、report v6、corrected file |

## 3. Profile v2 与资产合同

### 3.1 Profile v2

`schemas/profile/project_profile_v2.json` 要求新 profile 显式提供：

- `profile_contract_version: 2`；
- `name`、`language_pair`、`source_lang`、`target_lang`；
- `wordcount_basis`；
- 完整 `scoring_policy`；
- `assets`、`context_pipeline`、`capabilities`；
- 必需 foundation capability：`context.core@1` 和 `source_provenance@1`。

`context_pipeline.mode` 定义 optional 能力是否影响正式审校：

| 模式 | 行为 |
|---|---|
| `off` | 只使用 foundation 能力；不让 optional context 影响正式结果 |
| `shadow` | 解析 optional context 并生成审计产物，不进入正式 packet、去重、建议或报告语义 |
| `enforce` | 将协商成功的 optional context、资产和约束纳入正式流程 |

Profile 的 `module_context_views` 为每个模块声明：

- 可见 capability；
- 评审 dimension；
- 可见 `constraint_kinds`；
- 邻句的 before/after、是否允许 target、边界模式；
- 单实体事实、关系和运行案例的数量上限。

如果模块视图启用 `language_policy.*` 且使用约束，必须声明非空 `constraint_kinds`。否则 profile 在协商阶段失败，不允许“规则已解析但 worker 没看到”。

### 3.2 项目资产

`schemas/profile/project_asset_v1.json` 对每个资产要求：

| 字段 | 含义 |
|---|---|
| `kind` | 资产类型，例如 style guide、entity registry、context rules |
| `path` | profile 目录下的声明路径 |
| `required` | 缺失时是否中止初始化 |
| `authority` | 事实或规则的发布方与权威级别 |
| `provenance` | 原生、派生或其他来源类型 |
| `distribution` | `public_allowed` / `internal_only` / `redacted` |
| `availability` | `included` / `external` |
| `content_schema` | 可选的 canonical 内容 schema |

引擎只加载 profile 显式登记且 capability 已启用的资产；目录中新增文件不会自动进入 worker。`external` 只能作存在性与来源声明，不能被当作当前运行时已读内容。

### 3.3 Capability 描述与协商

`schemas/profile/capability_descriptor_v1.json` 定义安全的声明式扩展：

- 字段类型仅允许 string、integer、boolean、enum；
- 基数仅允许 one/many；
- normalizer 只能来自内置 allowlist；
- 声明适用条件、列候选、模块视图和邻句窗口；
- 禁止任意 Python 路径、模板指令或其他可执行配置。

`scripts/lqe_capabilities.py` 将 legacy/v2 profile 规范化为统一形状，然后对 runtime、asset 和 provider 进行协商。`schemas/context/capability_resolution_v1.json` 保存：

- profile/runtime 版本；
- pipeline mode；
- enabled capability 的 effect、descriptor/config/asset/provider digest；
- disabled capability 的结构化原因；
- warnings 和整体 digest。

Required capability 不支持、必需资产缺失或 provider 与目标语不一致时，`read` 失败。Optional capability 可记录 disabled 后继续，但不会伪造空能力。

### 3.4 Canonical context schemas

| Schema | 用途 | 关键边界 |
|---|---|---|
| `lqe.entities` | 实体、别名、已验证事实与关系 | 实体事实不授予术语替换权 |
| `lqe.review-examples` | 已审案例、维度、作用域、用途 | `regression_only` 不得进入运行输入 |
| `lqe.context-rules` | 已确认/草案/废弃/驳回规则 | 只执行 confirmed，由可信 provider 解析 |
| `lqe.project-source-manifest` | 原始资料、派生资产与导入覆盖率 | `unmapped` 必须为 0 才可发布 |
| `lqe.segment-context-overrides` | 项目级 canonical 逐句补充 | 只允许 verified、已声明字段 |
| `lqe.job-context-overrides` | 当次任务的已核实 sidecar | 绑定 segment set、key、source digest 和授权源 |
| `lqe.context-gap-report` | 客观记录上下文缺口 | 区分 not provided、unresolved/ambiguous alias、not applicable |
| `lqe.context-bundle` | 每模块、每句的实际上下文 | 绑定 segment/asset/capability/view 摘要 |
| `lqe.worker-context-manifest` | worker 实际可读资源及预算 | 安全 locator、digest、byte count 必须一致 |
| `lqe.selected-context-evidence-index` | checker 实际选取的逐模块/逐句证据 | suggestion 只能使用其严格并集 |

状态不能混用：实体事实使用 `verification_status`，上下文规则使用 `rule_status`，案例使用 `review_status`，术语使用 `confirmed/protected`。

## 4. 输入预处理与顺序

### 4.1 Adapter 与标准句段

`lqe_io.py read` 先通过 adapter 生成统一句段包装：

- 表格：CSV、TSV、XLSX、XLSM 和只读 `.xls`；
- SDL：带 SDL namespace 的 XLIFF 1.2 / SDLXLIFF 1.2；
- 共同字段：`id`、`segment_key`、source/current target、保护状态、input status、context、provenance。

列绑定优先级为：显式 CLI 参数 → profile 唯一映射 → 内置安全唯一别名 → 空。同一字段同时命中多列时失败，不默认取第一列。

有业务 key 时使用输入 key；否则由输入 digest、容器和行坐标生成稳定 key。Generated key 可绑定当次 artifact，但不用于跨版本 pivot join。

### 4.2 Input guard

Input guard 检查：

- 多 sheet 时主 sheet 是否明确；
- 必需列、行宽与显式 key 是否唯一；
- source digest 与目标来源声明是否一致；
- 已声明 pivot compare 是否存在 authoritative 冲突；
- 输入路径与输出/资产是否为同文件、软链、硬链或大小写别名。

Pivot 四件套 `--pivot-sheet`、`--pivot-key-col`、可重复 `--pivot-compare`、`--pivot-authority` 必须同时提供，且必须显式给出 `--key-col`。目标译文没有 source digest 证据时产生 `UNVERIFIED_TARGET_PROVENANCE`，与当前 source 不一致时产生 `TARGET_SOURCE_VERSION_MISMATCH`；pivot 比较不一致使用 `SOURCE_VERSION_MISMATCH`。`authoritative` 会 block，`diagnostic` 只警告。

已确认的句段级版本冲突写为 `blocked`。Blocked 句仍保留全 ID 覆盖，但不进 AI、不计分、不生成建议、不修改译文。

### 4.3 固定上下文应用顺序

正式句段在 staging 中按下列顺序处理：

1. 从输入列提取已声明的 core/extension 字段。
2. 应用 profile 资产中的 canonical `segment_context_overrides`。
3. 应用当次 `--context-overrides` 已核实 sidecar。
4. 重新计算 extension 的 ready/incomplete/conflict 状态。
5. 用当前已绑定的上下文解析 language/context rules。
6. 生成 `segment_revision_digest` 和各模块 equivalence key。

因此固定优先关系为：

```text
project canonical override → verified job sidecar → language/context rules
```

左侧是事实值的起点，当次 sidecar 只能在 key、source digest、授权、声明字段与 `expected_context` 都匹配时进行已验证修正。右侧 rules 不覆写事实，而是基于当次最终事实解出结构化 constraints。

### 4.4 原子发布

`read` 在临时 staging 目录内完成资产复制、schema 验证、上下文应用、来源复核和 state 构建，最后才以 `state.json` 为终点原子发布。任一步失败不留正式半套 job。

## 5. Context bundle、邻句和模块投影

`scripts/lqe_context_bundle.py` 从 state 和已绑定资产确定性派生每模块 context bundle。Bundle 至少绑定：

- segment identity、source、current target、input/protection 状态；
- `segment_revision_digest`；
- `project_asset_snapshot_digest`；
- `capability_resolution_digest`；
- 实际 module view；
- 实体事实 ID、关系 ID、约束、邻句、案例和术语证据 ID；
- 每类选取过程的 digest。

选取规则：

- 只投影 module view 声明的 capability/dimension/constraint kind；
- 实体别名只在唯一解析后可用；未解析或多义别名只形成 gap；
- 只选已验证/有来源事实，`runtime_rule:false` 关系不进正式 bundle；
- `regression_only` 案例不参与运行选取；
- `max_runtime_examples: 0` 意味着不提供案例，不是自动选取；
- 邻句优先受 scene/group 边界限制；`strict` 缺边界时标记 incomplete，`same_if_present` 可记录 fallback；
- blocked/protected 句不作邻句；只有 view 明确允许时才提供邻句 target。

去重使用“模块实际投影 + source/current target + input/protection”的 equivalence key。两句文本相同但 speaker、关系、约束或邻句不同时，只要差异进入该模块视图，就不得广播同一审校结果。

## 6. Checker 证据与 worker receipt

### 6.1 Review packet

`lqe_review.py prepare` 为当前 split generation 生成：

- module-specific review packet v3；
- `batch_plan.json`；
- `cost_report.json`；
- 每批 `bundle_set.json` 和 `worker_manifest.json`；
- `selected_evidence_index.json`。

Worker 上限为：

- 每 worker 最多 4 个 packet；
- source + target 最多 25,000 字符；
- instructions、资产、source-manifest compact projection、bundle 和 packet 总输入最多 100,000 bytes。

`worker_context_manifest_v1.json` 必须完整带有 `profile`、`capability_resolution`、`project_asset_snapshot`、`project_assets`、`language_providers`、`source_manifests`、`language_notes`、`worker_documents`、`instructions.common/module/suggestions`、`shared_context_assets`、`context_bundles`、`packet_payloads` 和 `budget`。空资源组仍要显式保留合同形状。

超限时拆批；不可再拆的最小单元仍超限时失败，不截断资料。Worker manifest 中可读资源只允许 `job_relative`、`skill_relative` 或 `embedded_text` locator，路径、摘要和字节数都需实时复核。

### 6.2 Selected evidence index

`selected_context_evidence_index_v1.json` 不记录“profile 最多允许什么”，而记录每个 checker 对每句实际选了什么：

- module + segment identity/source/revision；
- context bundle 和 module view digest；
- 实体事实、关系、运行案例、术语证据 ID；
- resolved constraint digests；
- 已选邻句的身份、source/context/target digest 和 target status；
- 选取过程的总 digest。

该索引同时绑定 packet、batch plan、worker manifest 和正式 module publication receipt。Suggestion 阶段必须使用所有必需 checker 证据的严格并集；模块缺失、索引过期或束绑不一致时失败。

### 6.3 Worker receipts 与发布

Checker 紧凑草稿必须提供：

- packet/batch/context/evidence digests；
- 完整 `reviewed_ids`；
- 只含有问题 ID 的 `findings`；
- 实际 `worker_id` 和当次唯一 `run_id`。

Publisher 重新派生实时 packet，校验全 ID 覆盖、模块类别责任、precheck 引用、worker receipt 和所有 digest，然后补齐 `issues: []` 并生成本地 publication receipt。模型草稿不能自报 AI provenance。

Suggestion generation worker 与 verifier 的 worker ID/run ID 各自都必须与 checker 不同，两者之间也必须不同。多批任务每批都要使用新 receipt。

## 7. 术语执行权限

术语分为三层责任：

1. 程序负责给出当前 source 的 exact term hit、候选译法、`confirmed/protected` 和切片证据。
2. 术语 checker 根据当前句子和已选上下文决定该词条是否适用。
3. 后续建议生成和发布必须服从该正式结论，不能自行重新选术语证据。

自动局部修改的程序闸门为：

- 必须存在 source exact hit；
- 候选必须 `confirmed: true`；
- 当前替换必须唯一、可定位且不损害保护内容；
- edit 必须引用与 hit 一致的 `confirmed_term` source/target 证据；
- Python 在合并前重新验证区间、切片、证据和唯一性。

术语 checker 通过 `resolution_status` 明确交接：

| 状态 | 后续权限 |
|---|---|
| `resolved` | 可在安全、唯一的局部修改合同内处理 |
| `reference_allowed` | 术语表不授权强制改词；可从 source 正常生成参考译文，必须独立验收 |
| `human_choice_required` | 必须人工选择；整句 suggestion 硬拒绝 |
| `conflict` | 权威资料冲突；整句 suggestion 硬拒绝 |

近似词、不同源词和未确认候选不能继承 exact term 的替换权；它们可以以 `non_authorizing_evidence` 形式记录为参考证据。`protected: true` 或受保护句永不修改。

## 8. Suggestion source-first 与独立 verifier

### 8.1 七层产物链

```text
generation packet v5
  → generation draft v5
  → candidate artifact v1
  → review packet v1
  → review draft v1
  → review artifact v1
  → final reference suggestions v5
```

Generation 的持久化资源位于 `suggestion_context/`，verifier 的持久化资源位于 `suggestion_review_context/`；两套目录分别绑定自己的 packet、batch plan、bundle set 和 worker manifest，不能共用 worker receipt。

每层都绑定 state revision、results basis、asset snapshot、capability resolution、context bundle set、worker context manifest、protection signature 和上游 artifact digest。ID 集必须完整覆盖已入选句段，不允许静默丢句。

### 8.2 Source-first 候选

生成 worker 以 source 为唯一语义依据，原译只用于保留变量、标签、换行、保护文本和已验证局部修改。草稿必须提交：

- `source_semantics`：subjects、actions、objects、negation/polarity、modality、speech act、text function、intensity、omissions、unsupported additions；
- `tone_decision`：register、politeness、是否依赖缺失的 dialogue context、证据和 uncertainties。

正式候选的 `tone_decision.uncertainties` 必须为空。若缺口已通过中性措辞或不使用未知称谓/代词/礼貌等级规避，将规避理由写入 evidence；若未知信息仍会改变措辞，必须 abstain。

候选必须处理该句的全部 `known_issues`，不只是触发入选的 Major/Critical 问题。Legacy issue 没有显式 `resolution_status`、状态为 `human_choice_required` 或 `conflict`、input blocked、保护句和 constraint conflict 在生成前硬拒绝。`reference_allowed` 不授权强制替词，但允许 source-first 整句生成并进入独立验收。仅出现 `needs_confirmation: true` 且 `edit: null` 不足以单独推导为硬拒绝，必须看正式 resolution 状态。

### 8.3 候选路由

Schema 保留 `hard_reject`、`deterministic_accept` 和 `independent_verifier` 三种 route。当前基线的正式行为是：

- 确定性闸门失败或 worker abstain 进入 `hard_reject`；
- 所有模型生成的整句候选都进入 `independent_verifier`；
- 不允许模型候选以 `deterministic_accept` 直接进 final。

### 8.4 独立 verifier

Verifier 读取与 generation 相同的 checker strict union，不能修改候选文本，只能返回 `accept | reject | human_required`。它必须分别检查 11 项：

1. subjects；
2. actions；
3. objects；
4. polarity/negation；
5. modality；
6. speech act；
7. text function；
8. intensity；
9. omissions；
10. unsupported additions；
11. tone/register/politeness/voice。

`accept` 要求 11 项全部 `pass`；任一 `fail` 或 `uncertain` 都只能拒绝或交给人工。候选 digest 必须原样复制，verifier draft 不含候选文本，因而无法暗中改写。

Final 只纳入 verifier accept 的候选；其余 ID 带 reason codes 进入 `excluded_ids`。Final 建议仍仅供报告展示，不进 corrected/apply/export。

## 9. Runtime 与 artifact 版本

| 对象 | 当前版本 | 用途 |
|---|---:|---|
| Profile contract | 2（同时兼容 legacy 1） | 资产和能力声明 |
| Job runtime contract | 2 | 当前可续跑任务的运行边界 |
| State artifact contract | 1 | 保留既有 state 主版本 |
| Context contract | 1 | state 内的上下文子合同 |
| Capability resolution | 1 | 当次能力协商结果 |
| Split contract | 1 | generation 和 state fingerprint |
| Review packet | 3 | 模块输入与证据绑定 |
| Suggestion generation packet/draft | 5 | source-first 生成 |
| Candidate artifact | 1 | 确定性路由后的候选 |
| Suggestion review packet/draft/artifact | 1 | 独立验收 |

Legacy profile 可经 adapter 创建 runtime v2 新 job，其 optional context 默认 `off`。已存在且缺少 `job_runtime_contract_version: 2` 的历史 job 只读；不得在原目录内重新 split/review/calc/write/export/suggest。需续跑时使用 `lqe_io.py reread` 从原输入原子创建新 job。

## 10. Report v6

Report v6 保持三张可见工作表：

1. `说明·导读`；
2. `LQA Scorecard`；
3. `LQE Results`。

`_LQE_CONTRACT` 保持 veryHidden，绑定：

- state digest；
- results digest；
- Results 可见内容 digest；
- Scorecard 可见内容 digest；
- runtime/context 版本；
- context audit headers。

可见审校区保持 10 列合同不变。Results 隐藏审计区增加 Segment Key、Input Status、Content Type、Context Status/JSON/Provenance/Digest、Resolved Constraints、Capability Resolution Digest 和 Project Asset Snapshot Digest；`LQE_Iter` 仍必须为最后一列。

报告验证要求 state/results 全 ID 覆盖、逐问题 provenance 和隐藏 context 值与当前运行实体精确一致。任何可见内容、审计行结构或绑定摘要被篡改后，合同验证失败。

## 11. 失败关闭策略

| 情况 | 行为 |
|---|---|
| Profile/schema/capability 不合法 | `read` 失败，不发布 state |
| Required asset/provider 缺失 | 初始化失败 |
| Language policy view 未声明 constraint kinds | profile 协商失败 |
| 必需列缺失或一字段命中多列 | 整次 read 失败 |
| 显式 key 重复、source digest 漂移 | read/sidecar 失败或句段 blocked |
| Sidecar 未授权、未验证、越权字段、expected value 漂移 | 整批拒绝，不修改原 job |
| 实体别名未解析/多义 | 记录 gap，不授权人物事实；依赖它的候选弃权 |
| Constraint 证据不足/冲突 | 不自动判错或改写；必要时 hard reject |
| Worker 输入超过 100,000 bytes | 拆批；单元仍超限则失败，不截断 |
| Review ID 覆盖不全、receipt 缺失/复用 | publisher 拒绝 |
| Checker evidence index 缺模块或 digest 过期 | suggestion prepare/publish 拒绝 |
| 术语需人工选择或权威资料冲突 | 整句 suggestion 拒绝 |
| 正式 tone decision 仍有 uncertainty | candidate publisher 拒绝，必须 abstain |
| Verifier accept 但任一语义项非 pass | review publisher 拒绝 |
| State/results/context/protection 或上游 artifact 变化 | 旧 artifact stale，拒绝继续发布 |
| 报告可见内容或隐藏审计漂移 | report contract 验证失败 |

“Fail closed”不等于所有缺口都中止整个 job。不影响当前措辞的缺口可显式记录后继续；会改变审校或候选结论的缺口才阻断对应模块或句段。

## 12. 安全与分发边界

- 原始资料用于 onboarding、转换覆盖校验和审计；正式 worker 读 canonical snapshot，不直接解析原始资料包。
- `project_source_manifest` 的完整版仅做 runtime live validation；worker 只读已计入预算的 compact projection。
- 所有 worker 资源由安全 locator、SHA-256 和 byte count 绑定；不允许越出 job/skill 根的路径。
- Context 是数据而不是指令。备注、事实和案例文本不能改变 worker 输出合同或提升自身权限。
- 公开包按 `distribution=public_allowed` allowlist 组装；`internal_only`、原始资料、人工终稿和 regression-only 答案不得进公开包。
- 公开 base profile 不得强引用未分发的内部资产。内部资产通过显式 profile overlay 加载，合并前后 digest 都进入 state。
- 内部包也应使用 allowlist，明确标注使用范围，并排除 job、输入、输出、缓存、备份、Git 元数据和未声明原件。
- 发布扫描禁止真实机器的敏感绝对路径；专门验证路径拒绝的合成负例可保留在 test fixture 中。ZIP entry 名本身仍一律禁止绝对路径和路径穿越。

## 14. 开发与扩展流程

### 14.1 新建或升级 profile

1. 确定稳定 profile ID、语言对、词数基准和评分策略。
2. 为每项 active asset 声明 kind/path/required/authority/provenance/distribution/availability。
3. 将原始资料转为所需 canonical assets，生成 source manifest 和逐单元 coverage；保证 `unmapped=0`。
4. 只声明真正有数据和消费者的 capability；未提供的业务事实保持未知。
5. 为每个模块配置最小必要 view、邻句窗口、数量上限和 constraint kinds。
6. 首先用 `shadow` 比较覆盖率与预算，通过后新建 `enforce` job；不修改历史 job。
7. 对输入、context bundle、checker receipt、suggestion 链和报告合同运行回归。

### 14.2 新增通用 context extension

1. 用 declarative descriptor 声明 capability ID、字段类型、列候选、适用条件和 module views。
2. 确认所需 normalizer 已在安全 allowlist；若不在，先扩展并单测核心 normalizer，不以 profile 代码注入实现。
3. 验证该字段可贯穿 read → state → module projection → equivalence digest → report audit。
4. 对 applies/not applicable/incomplete/conflict 四类路径建立 fixture。
5. 用 synthetic mixed-content fixture 验证未适用句段不被误要求补字段。

### 14.3 新增目标语规则

1. 使用仓库内可信 provider，实现 `validate_policy`、`resolve`、`observe`、`evaluate`。
2. 在 registry 中固定 provider ID、API version、target language 和 descriptor digest。
3. Profile 声明 language capability/provider/context-rules asset，且消费模块显式声明 `constraint_kinds`。
4. 测试 confirmed/draft/rejected、有效期、适用性、权威/优先级、同级冲突和目标语不匹配。
5. 验证约束能同时进入 checker bundle、selected evidence index、suggestion strict union 和 candidate 后置检查。

### 14.4 修改 suggestion/review schema

1. 先更新 JSON Schema 和 Python 语义校验器。
2. 为正常、缺字段、错类型、部分 ID、stale digest 和 receipt 复用增加测试。
3. 更新 generation/verifier 指令，确保 prompt 和 publisher 使用同一合同。
4. 不原地重释旧 artifact；必要时升版并显式拒绝旧版续跑。

## 15. 兼容与迁移

### 15.1 Profile 兼容

- 无 `profile_contract_version` 的旧 profile 按 legacy v1 规范化，context mode 默认 off。
- Legacy profile 新建的 job 仍使用 runtime v2 的绑定、发布和报告合同。
- 升级到 v2 后，仅启用 profile 显式声明且协商成功的能力。
- 公开 base + 内部 overlay 允许同一项目在不泄露资产的前提下复用同一引擎。

### 15.2 Job 兼容

- Runtime v2 job 可按当前链路续跑，但任何 state/asset/context/instruction 变化都要重建下游 artifact。
- Historical runtime v1 job 只可查看或按原合同验证现存产物。
- 续跑历史任务时使用 `reread --from-job ... --input ... --job ...`；程序复核输入摘要、列/格式和句段覆盖后创建新 job。
- 无原输入或输入摘要不符时不迁移，不从旧 state 伪造新输入证据。

### 15.3 上线步骤

```text
legacy/off baseline
  → profile v2 core
  → canonical assets + coverage
  → shadow context audit
  → enforce synthetic regression
  → project canary
  → clean allowlist package
```

切换 off/shadow/enforce 会改变 capability resolution digest，因此必须新建或重建 job 产物，不能把旧 packet 直接当新模式使用。

## 16. 已知限制

- 管线可以显式管理上下文缺口，不能凭空补齐客户事实。
- `.xls` adapter 保真行列值和坐标，不承诺 BIFF 格式、批注、绘图或公式等价；corrected 固定输出 `.xlsx`。
- `.xlsm` 后缀已支持读取，但当前没有独立的 `.xlsm` 专用 fixture；宏和 VBA 保真不在当前导出合同内。
- 当前 SDLXLIFF 支持读取和导出五列 corrected workbook，不回写 XML。
- 案例检索是可审计的确定性筛选，当前不依赖向量数据库或在线 RAG。
- 字节预算是硬上限；单句与必需资料已超限时只能减少 profile view 或补充更紧凑的 canonical projection，不能截断后继续。
- 只有已登记目标语 provider 才能做程序化语言约束观察；未登记语种仍可运行通用 LQE，但不会伪造 provider 结论。
- 独立 verifier 降低生成 worker 自我放行风险，但不是对翻译正确性的数学证明；高风险建议仍在报告中标记待人工确认。
- 项目资料声明为 `external` 且当前环境不含原件时，只能验证 canonical asset digest，不得声称本次已重新对照原件。

### 18.3 摘要依赖图

摘要不是日志字段，而是复用许可。主要依赖如下：

```text
profile + overlay + declared asset metadata + bound asset bytes/status
  → project_asset_snapshot_digest

normalized profile + runtime capability registry
  + project asset snapshot/status + trusted provider descriptor
  → capability_resolution_digest

input bytes + row/container + source/current target + guard
  + formal context + resolved constraints
  + capability resolution + asset snapshot + job sidecar
  → segment_revision_digest

state revision + precheck + terms + scope + split options
  → split_fingerprint
  → chunk payload digests

split + module view + context bundle + worker resources
  → review packet digest
  → module output v2 + publication receipt v1

verified results + selected evidence strict union + protection signature
  → suggestion generation packet v5
  → candidate v1
  → review v1
  → final v5

state + verified results + visible workbook content
  → report contract v6
```

任一上游摘要变化时，下游旧产物必须视为 stale。不得只改 JSON 中的摘要字段来“续上”旧链。

### 18.4 代码层全局不变量

- Profile 只声明数据和安全配置，不执行任意 Python、命令、模板或 prompt。
- 原始资料只用于导入、追溯和覆盖率核对；worker 只读取已声明、已绑定的运行资料。
- `shadow` 数据不能进入正式 bundle、equivalence key、checker 结果或 suggestion。
- 业务 key、source digest、目标来源证明和 pivot join 各自承担不同责任，不能互相替代。
- Context 的值、适用状态和 provenance 必须一起传播；只复制值会丢失可审计性。
- Checker 负责发现和分类问题；Python 负责合同、范围、局部 edit、保护内容和摘要验证。
- Suggestion generation 与 verifier 必须是不同 worker，且都不能冒充 checker。
- 模型生成的整句候选没有 deterministic 直通 final 的路径。
- Report-only reference suggestion 不进入 `corrected`、`apply-fixes` 或 `export`。
- Current runtime 的正式链不得使用 `build-results` 绕过模块发布，也不得把 `ingest-corpus` 当作标准运行步骤。

### 21.2 稳定 CLI 操作面

| 目的 | 命令与必需参数 |
|---|---|
| 新建 job | `lqe_io.py read --input --project --out`；表格正式运行应显式绑定 sheet/source/target/key |
| 迁移 runtime v1 | `lqe_io.py reread --from-job --input --job`，可附加 overlay 和 verified sidecar |
| 校验 canonical override | `lqe_profile_ingest.py validate-overrides --input --segments --declared-extensions` |
| 生成缺口/草稿 | `lqe_context_overrides.py gaps --state --out` / `scaffold --state --out` |
| 准备/发布 checker | `lqe_review.py prepare --job` / `publish --job --chunk --module --input` |
| 准备/发布候选 | `lqe_suggestions.py prepare --job` / `publish-candidates --job --input` |
| 独立复核/终稿 | `lqe_suggestion_review.py prepare --job` / `publish-review --job --input` / `publish-final --job` |
| 计分/报告/导出 | `lqe_calc.py --state --errors`，`lqe_io.py write --state --errors --score`，正式导出使用 `lqe_io.py export --state --errors` |

`lqe_suggestions.py publish` 是故意保留的旧入口，当前必须失败；不得用它绕过 candidate/review 链。运行文档不应推荐 `build-results` 或 `ingest-corpus`。

### 21.3 TOCTOU、别名与摘要失效

- Prepare 只是生成待处理快照；publish 必须从当前 state 重建 live packet，再核对 packet/bundle/evidence/manifest digest。
- Worker 在开始和发布前都通过 `verify_worker_context_manifest_resources` 重读 locator；字节数或 SHA 变化即拒绝，这是资源 TOCTOU 边界。
- `job_relative` 和 `skill_relative` 必须解析到各自根内的普通文件；`embedded_text` 按 UTF-8 字节计费。软链、越界、不一致大小写均失败。
- 列别名按 CLI 显式绑定、profile 唯一映射、内建安全别名的顺序解析；多列命中不猜测。实体别名只有唯一解析后才可提供事实。
- 去重键必须包含该模块的实际 context projection。不可见字段不影响该模块等价性；可见的 speaker、relation、constraint、neighbor 变化必须拆分。
- Profile、overlay、asset、provider、sidecar、source/target、protection、context 或 instruction 的任一绑定变化，都会通过 revision 链使下游 receipt 失效。

### 21.4 发布、回滚与异常处理

| 阶段 | 异常 | 恢复动作 |
|---|---|---|
| read | source/pivot/version guard block | 更正来源证明或输入，新建 job；不改 state 解除 block |
| context | alias 未解或冲突 | 通过 gap/scaffold 取得授权核实，以 sidecar 重读 |
| checker | locator/digest/receipt 失效 | 废弃该 worker 输出，从 prepare 重建 batch |
| suggestion | 候选或证据链 stale | 重跑 suggestion prepare，不复用 draft |
| verifier | worker 不独立或 11 项非全 pass | reject/human required，不改候选文本 |
| report | visible/hidden digest 不一致 | 从已验 results 重新 write，不手改 contract |
| release | 白名单、CRC、路径或嵌套 Office 扫描失败 | 丢弃 staging/ZIP，从 clean baseline 重建 |

发布使用白名单 staging，生成 `BUILD_INFO.json`、`SHA256SUMS` 和外层 ZIP SHA-256，再在新解压目录运行全量测试、profile smoke、JSON/ZIP/Office 结构检查与敏感资料扫描。回滚是恢复前一个已验证包和新建 job，不将新产物倒写进历史 runtime v1 目录。
